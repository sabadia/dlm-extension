# E0.8: how long the Chrome service worker lives

**Question.** What keeps a Manifest V3 service worker alive long enough to watch for live updates or an expired link?

**Method.** The worker sent a heartbeat to a local server every 2 s and the runner measured the gap after which the
heartbeats stopped (the worker was terminated). Chrome for Testing 156, headless, 130 s per run.

| Variant                                                             | Worker alive    | Notes                                                                                                                                                   |
| ------------------------------------------------------------------- | --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Idle (timers only)                                                  | about 28 s      | Terminated after about 30 s without an extension event. Timers and outgoing `fetch` do not extend it.                                                   |
| Open `fetch` stream to the daemon's SSE                             | about 28 s      | The stream delivered one chunk (the daemon's heartbeat at 15 s) and the worker still ended at about 30 s: **a streaming fetch does not keep it alive.** |
| `alarms` every 30 s                                                 | the whole 130 s | Each alarm is an event that restarts the idle timer.                                                                                                    |
| `connectNative` to the host with a ping every 20 s (origin allowed) | the whole 130 s | Messages over the port keep it alive.                                                                                                                   |

Other observations:

- Without the extension id in the daemon's `allowed_origins`, the native host exits at once ("Native host has exited").
  With it, `connect` returns `baseUrl`, `token`, `running`, `version`.
- In the native run the first reply arrived about **66 s** after start, though the host answers in 20 ms when run by
  hand. Cause (reported by the maintainer, who was away from the machine): **macOS showed a permission prompt** the first
  time the browser started the host, and the host only ran after it was approved. It is not a slow host. Consequence for
  the product: the first connection on a Mac can wait for a prompt the user must answer, so onboarding (E5.3) must say so
  and the extension must treat "no answer yet" as "waiting for the system", not as a failure. Which prompt it was is not
  recorded; note it in the first real-Chrome check (E7.6).

**Decision.**

- The worker holds **no long-lived stream**. Live progress uses SSE **only while the popup is open** (the popup page
  stays alive and can read a streaming `fetch`).
- Watching for `awaiting_link` and other background needs uses an **alarm every 30 s** with a short poll
  (`GET /v1/tasks?status=awaiting_link`), or the daemon's new event (P14.6) read on those wake-ups, so the cost is a
  request every half minute only when the refresh feature is on.
- A native port is not kept open just to hold the worker awake.
- Everything that matters lives in `storage.session` / `storage.local` (already a convention), because the worker is
  restarted often.
