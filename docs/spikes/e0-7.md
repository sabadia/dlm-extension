# E0.7: handing a browser download to DLM

**Question.** How do we take over a download in each browser, how fast, and what is left behind?

**Method.** Real downloads from a local server: an attachment (`Content-Disposition`), a redirect to an attachment,
an `application/octet-stream` response without a disposition, an inline text file, a blob link clicked by a script,
and a download started by the extension itself. Three modes: observe, cancel-and-erase on `downloads.onCreated`, and
(Firefox) cancel in a blocking `webRequest.onHeadersReceived`.

**Results.**

|                                                                 | Chrome 156                                                                                      | Firefox 159                                                                                              |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Response headers seen (`webRequest`) before the download exists | yes, 1 to 6 ms before `onCreated`                                                               | yes, 7 to 9 ms before                                                                                    |
| `onCreated` item                                                | `url` = address before redirects, `finalUrl`, `referrer` (empty here), `mime`, `filename` empty | `url` = address after redirects, **no** `finalUrl`, **no** `referrer`, `mime`, `filename` already a path |
| Cancel + erase from `onCreated`                                 | cancelled in about 10 ms (`USER_CANCELED`), erased, **no file** on disk                         | cancelled in 1 to 40 ms, erased, **no file** on disk                                                     |
| Blocking `webRequest`                                           | not possible in MV3                                                                             | cancels attachments **before any download appears** (no `onCreated`, no file)                            |
| Redirect then attachment                                        | handled the same                                                                                | handled the same                                                                                         |
| `octet-stream` without disposition                              | downloaded, `onCreated` fires, can be cancelled                                                 | same                                                                                                     |
| Inline text                                                     | no download                                                                                     | no download                                                                                              |
| Download started by the extension itself                        | `onCreated` fires (`byExtensionId` set)                                                         | `onCreated` fires (`byExtensionId` set)                                                                  |

**Findings that change the design.**

1. **One common path.** `downloads.onCreated` then `downloads.cancel` then `downloads.erase` works on both browsers and
   leaves nothing on disk. It is the v1 path. Firefox's blocking `webRequest` is an optional refinement (no flash of a
   download entry); it is not needed for correctness, so E2.3 shrinks to Firefox-specific details.
2. **Use the headers that arrive first.** Keep a short-lived map (a few seconds, keyed by request id and URL) of
   `Content-Disposition`, `Content-Type`, `Content-Length`, `tabId` and `documentUrl` from `webRequest`, and read it when
   `onCreated` fires. Firefox's item has no referrer, so the page address must come from there.
3. **Never intercept our own download.** A blocking filter also cancelled the extension's own fallback download
   (`CRASH`). Fallback downloads must be recognised by `byExtensionId` (and an in-memory set of URLs we decided to
   release) and exempted.
4. **Only intercept `http`, `https` and `ftp` URLs.** A `blob:` or `data:` download cannot be fetched by the daemon;
   leave it to the browser. (A script-clicked blob link without a user gesture produced no download in either
   browser, so a real blob download was not measured here; it needs a user gesture and goes to the manual list.)
5. **Event pages need listeners at load.** In Firefox, a `webRequest` listener registered after an `await` saw no events;
   the same listener registered at the top level saw all of them. This is a rule in `docs/CONVENTIONS.md` and is
   now tested in the spike results.

**Not covered.** Downloads started by other extensions, downloads in private windows, POST downloads (E6.5), large
downloads where cancelling late matters (the cancel always came within about 100 ms of `onCreated`).
